# Telesio Onboarding Lite

MVP d'onboarding : RH saisit une demande, la direction valide, l'app prépare le compte Entra et un dossier SharePoint, puis RH active le compte le jour J.

## Flux

1. **Demande (RH ou Direction).** RH ou la direction saisit la demande (prénom, nom, poste, département, responsable, date d'arrivée).
2. **Validation (direction).** La direction voit la liste des demandes `EnAttente` et les valide ou les refuse.
3. **Préparation.** À la création, le compte Entra est **désactivé** (attributs natifs `employeeHireDate`, `manager`, `jobTitle`, `department`, `usageLocation` = `FR`). À la validation, l'app réserve la licence (voir « Licence »), ajoute le compte (toujours désactivé) au groupe des arrivants, puis crée le dossier SharePoint.
4. **Jour J.** RH (ou la direction) clique sur « Activer » : le compte est activé (il est déjà dans le groupe des arrivants depuis la validation), un **mot de passe temporaire** est posé avec `forceChangePasswordNextSignIn: true`, affiché une seule fois et remis en main propre, puis le statut passe à `Actif`.
5. **Fin d'onboarding.** À la première connexion (PC en OOBE Autopilot ou n'importe quel service Microsoft), l'accès conditionnel du groupe des arrivants impose d'inscrire Microsoft Authenticator, puis Entra impose de changer le mot de passe (ordre constaté sur test le 2026-10-29). Quand le mot de passe a changé après la remise **et** qu'Authenticator est inscrit, **une tâche de l'application** (toutes les 5 minutes, voir « Passage à Terminé ») termine le compte : il quitte le groupe des arrivants et le statut passe à `Terminé`, sans action de RH. Tant que ce n'est pas le cas, l'écran RH affiche l'état de l'onboarding (mot de passe, Authenticator).

**Pas de base de données.** L'état vit dans Entra, dans l'attribut d'extension `statutOnboarding` : `EnAttente`, `Validé`, `Refusé`, `Actif` ou `Terminé`.

## API RH (étape 2)

Les routes `/api` décident d'après les **droits** que `GET /api/moi` annonce à l'interface (Easy Auth, en-tête `X-MS-CLIENT-PRINCIPAL`, rôles du jeton) : `creer` (RH ou Direction), `approuver` (Direction), `activer` (RH ou Direction), `acces` (au moins un des trois). Sans le droit, la réponse est 403 `{ error: "Accès refusé", code: "droit_manquant" }` et le refus est tracé (`acces.refuse` : route, objectId, droit manquant). Il n'y a **plus de valideur désigné** : tout porteur du rôle Direction peut valider et refuser, **y compris ses propres demandes** (autorisé, tracé : voir « Auto-approbation »). Sans Easy Auth actif, l'app répond 503 (l'en-tête serait falsifiable). Les écritures n'acceptent que `application/json`.

- `GET /api/moi` (toute personne connectée, **sans rôle requis**) : `{ nom, email, roles, droits }` lus dans l'en-tête Easy Auth `X-MS-CLIENT-PRINCIPAL`, comme le contrôle des rôles. `nom` = revendication `name` (à défaut l'email, à défaut `""`), `email` = `email`, à défaut `preferred_username` (`null` si absent), `roles` = revendications de rôle dédoublonnées, valeurs tronquées à 256 caractères. Aucun appel Graph, `Cache-Control: no-store`, pas d'objectId ni d'autre revendication dans la réponse, rien n'est tracé en cas de succès (un refus l'est, comme pour les autres routes : 401 sans identité, 503 sans Easy Auth).
  - **`droits: { acces, creer, approuver, activer }`**, calculé côté serveur d'après `RH_ROLE` (défaut `RH`) et `DIRECTION_ROLE` (défaut `Direction`), c'est-à-dire `rh_role` et `direction_role` de Terraform : **RH** = `creer` et `activer` ; **Direction** = tous les droits de RH (`creer`, `activer`) **plus** `approuver` ; `acces` = au moins un des trois (donc `false` sans l'un des deux rôles). Comparaison exacte avec les rôles du jeton ; un rôle étranger ne donne rien. Ces droits sont **les mêmes** que ceux qui contrôlent les routes (voir ci-dessous). Pas d'autre contrôle d'identité : les rôles s'affectent dans Entra (voir « Easy Auth »).
  - `DIRECTION_ROLE` est un réglage d'application ajouté dans [infra/main.tf](infra/main.tf) : tant que Terraform n'est pas appliqué sur un environnement, l'app utilise le défaut `Direction` (identique à `direction_role` par défaut).
- `GET /api/annuaire?q=` (droit `creer`) : recherche du manager dans Entra (`$search` sur `displayName` et `mail`, comptes actifs, 10 résultats max). Retourne `id`, `displayName`, `mail`.
- `POST /api/demandes` (droit `creer` : RH ou Direction) : `{ prenom, nom, dateArrivee (AAAA-MM-JJ), poste, service, managerId, licence }`.
  1. Vérifie le manager, génère l'UPN `prenom.nom@<UPN_DOMAIN>` (minuscules, sans accents ni espaces), suffixe 2, 3… si pris.
  2. Crée l'utilisateur (`accountEnabled=false`, mot de passe aléatoire non stocké), avec `statutOnboarding=EnAttente`, `licenceOnboarding` et `createurOnboarding` (objectId de la personne qui saisit) **dans le même `POST /users`** (aucun compte sans statut ni sans créateur), puis `PUT manager/$ref` (réessayé tant que le compte n'est pas répliqué). Si le manager ne peut pas être posé, la demande existe quand même : 201 avec `avertissement: "manager_non_affecte"` (à poser dans Entra ; ne pas renvoyer la demande, ce qui créerait un doublon).
  3. 201 `{ id, userPrincipalName, statut }`, 400 `{ error, details }` si invalide, 409 si aucun UPN libre, 502 si Graph échoue (avec `etape`, et `id` du compte éventuellement créé), 503 avant toute lecture ou écriture si `ENTRA_CREATOR_EXTENSION` manque.
- **Créateur** : l'objectId du créateur (`createurOnboarding`, `ENTRA_CREATOR_EXTENSION` = `extension_<appId sans tirets>_createurOnboarding`, créée par Terraform dans [infra/graph.tf](infra/graph.tf), `prevent_destroy`) sert à **tracer** l'auto-approbation (voir « Auto-approbation »). Une demande créée avant cette extension n'a pas de créateur : aucune trace, elle reste validable. **Ordre de mise en service** : appliquer Terraform (extension et réglage d'application) **avant** de déployer l'app sur un environnement, sinon création, suivi, validation et refus répondent 503 ; dev le fait dans l'ordre (apply puis déploiement), test s'applique à la main.
- Prérequis Entra : l'extension de répertoire `statutOnboarding` doit exister (définie une fois sur une inscription d'application) ; `ENTRA_STATUS_EXTENSION` en porte le nom complet `extension_<appId sans tirets>_statutOnboarding`.

Traçabilité : événements personnalisés Application Insights (`demande.compte_cree`, `demande.echec`, `acces.refuse`…) avec l'objectId de l'acteur et de la cible, l'étape et le code d'erreur. Jamais de nom, UPN, terme de recherche ni mot de passe. L'auto-collecte HTTP/dépendances n'est volontairement pas activée (les URL contiendraient ces données).

## API Direction (étape 3)

**Tout porteur du rôle Direction** (`DIRECTION_ROLE`, droit `approuver`) peut lister les demandes, les valider et les refuser, **y compris les siennes** (voir « Auto-approbation »). Direction a aussi les droits `creer` et `activer` (activer, régénérer, terminer, liste des activations). L'identité vient d'Easy Auth, comme pour RH ; il n'y a plus de valideur désigné (`DIRECTION_TYPE` et `DIRECTION_OBJECT_ID` ne sont plus lus : s'ils subsistent dans les réglages d'un environnement, ils sont ignorés jusqu'au prochain `terraform apply`, qui les retire). Sans le rôle : 403 `droit_manquant`.

- `GET /api/demandes` (droit `approuver`) : comptes avec `statutOnboarding=EnAttente` (nom, poste, service, manager, date d'arrivée ; 1 000 max (10 pages de 100), `tronque` l'indique).
- `POST /api/demandes/:id/valider` (droit `approuver`) : licence d'abord (voir « Licence »), puis statut `Validé`, puis dossier SharePoint à la racine de `SHAREPOINT_DRIVE_ID` (site `SHAREPOINT_SITE_ID`), nommé selon `SHAREPOINT_FOLDER_PATTERN` (défaut `{nom} {prenom}`, caractères interdits retirés). Idempotent : un dossier existant est réutilisé (un fichier de même nom donne 502). Si SharePoint échoue, le statut reste `Validé` et la réponse est 502 avec `etape` ; **rappeler `valider` reprend uniquement le dossier** (`reprise: true`), ou `POST /api/demandes/:id/reprendre` (ci-dessous), que l'écran propose.
- `POST /api/demandes/:id/reprendre` (droit `approuver`, corps `{}`) : recrée le **dossier SharePoint manquant** d'un compte `Validé` (après un 502 de `valider`), **sans** refaire la licence, le groupe des arrivants ni le statut ; une seule écriture. Idempotent (un dossier existant est réutilisé : `dossier.cree: false`). 409 si le compte n'est pas `Validé`, 503 sans SharePoint, 502 avec `etape` si SharePoint échoue, 409 `action_en_cours` si un appel est déjà en cours. Reprendre n'approuve rien : aucune trace d'auto-approbation. Tracée : `demande.dossier` et `demande.reprise_dossier` (objectIds, jamais le nom du dossier).
- `POST /api/demandes/:id/refuser` (droit `approuver`) : `{ "motif": "…" }` obligatoire (500 car. max) ; le motif n'est tracé que par sa longueur et n'est conservé nulle part ; le compte est supprimé (corbeille Entra, récupérable 30 jours). Un échec de suppression laisse le compte `EnAttente` : on peut réessayer.
- **Auto-approbation** : **autorisée**. Une personne de la direction peut valider ou refuser la demande qu'elle a créée : plus de 403 `auto_approbation`, et `GET /api/suivi` lui propose `approuver` et `refuser` comme à toute la direction. Elle est **tracée** : quand l'acteur est le créateur de la demande (objectId enregistré à la création dans `createurOnboarding`, comparé sans tenir compte de la casse), `valider` et `refuser` émettent `demande.auto_approbation` (`outcome: ok`, objectId de l'acteur, objectId du compte, `operation` : `valider` ou `refuser`), une fois le statut contrôlé et avant les écritures (un 409 hors `EnAttente` n'en émet pas ; ni `reprendre`). Jamais de nom, d'UPN ni de motif. Les autres contrôles (droit `approuver`, statut, licence) sont inchangés. Sans `ENTRA_CREATOR_EXTENSION`, `valider` et `refuser` répondent 503 sans rien lire ni écrire (l'approbation ne pourrait pas être tracée) ; `GET /api/suivi` ne lit plus le créateur et n'en a pas besoin.
- 409 si le compte n'est pas un compte d'onboarding désactivé au bon statut (`valider` : `EnAttente`, ou `Validé` pour la reprise ; `refuser` : `EnAttente`). C'est le garde-fou qui empêche `refuser` de supprimer un autre compte.
- Les POST n'acceptent que `application/json` (corps `{}` suffisant pour `valider`).
- Homonymes : deux personnes au même `{nom} {prenom}` partageraient le dossier ; ajouter `{id}` au motif si le cas se présente.

## Licence (étape 6)

Licence **par groupe**, **choisie par RH** dans une liste déroulante du formulaire de demande. `LICENSES` est un tableau JSON `[{ "skuId", "libelle", "groupId" }]` : un SKU (`skuId` de `GET /subscribedSkus`, pas son `id`), son libellé affiché et son groupe de sécurité (appartenance affectée, non assignable à un rôle), un groupe par SKU (GUID valides, doublons refusés au démarrage). `ENTRA_LICENSE_EXTENSION` (`extension_<appId sans tirets>_licenceOnboarding`) est requis avec `LICENSES`. Exige Entra ID P1 (ou un SKU qui l'inclut) ; l'attribution aux membres est **asynchrone** côté Entra. `LICENSES` absent : les demandes, la liste et `valider` répondent 503 avant toute lecture.

**Cache.** `GET /api/licences` (affichage du formulaire RH) met `GET /subscribedSkus` en cache 60 s en mémoire, par instance, sans conserver les échecs. La création de demande et la validation direction relisent toujours en direct, et une validation ou un refus pour manque de licence vide le cache. Un changement fait hors de l'app (achat, attribution manuelle) peut donc mettre jusqu'à 60 s à apparaître dans la liste.

- `GET /api/licences` (droit `creer`) : `{ licences: [{ skuId, libelle, disponibles }] }`, `disponibles = enabled - consumedUnits` lu via `GET /subscribedSkus` (jamais négatif, 0 si le SKU est absent du tenant). Le groupe n'est pas exposé. Le formulaire affiche « libellé : N disponibles » et grise (désactive) les licences à 0.
- `POST /api/demandes` : champ `licence` (skuId) obligatoire. Hors liste : 400 (`details.licence`), aucune écriture. SKU à 0 : 409 « Aucune licence disponible » (`code : licence_indisponible`), aucune écriture. Sinon le skuId est stocké sur le compte dans l'extension `licenceOnboarding`, **avant** le statut (qui reste la dernière écriture). Pas de base de données.

`usageLocation = FR` est posé à la création du compte (sans lui Entra n'attribue rien) ; un compte créé avant cette étape doit recevoir `usageLocation` à la main, sinon `valider` répond 502 (`raison` typiquement `ProhibitedInUsageLocationViolation`). Une demande créée avant le choix de licence n'a pas d'extension `licenceOnboarding` : `valider` répond 409 (`code : licence_inconnue`), il faut la refuser et la recréer ; de même si le SKU stocké n'est plus dans `LICENSES`.

`valider` lit le compte (404 et 409 de statut inchangés), prend le SKU stocké sur le compte (extension `licenceOnboarding`, retrouvé dans `LICENSES`, sinon 409 `licence_inconnue`) et, **avant toute écriture**, avec le groupe de **ce** SKU :

1. Le compte porte déjà la licence sans erreur (reprise, tentative précédente) : rien à faire, pas de décompte. Sans ce cas, le compte compterait dans `consumedUnits` et la reprise serait refusée à tort.
2. Sinon `GET /subscribedSkus` : `prepaidUnits.enabled - consumedUnits`. À 0 (ou moins) : **409 « Aucune licence disponible »**, le statut ne change pas, rien n'est écrit. SKU absent du tenant : 503.
3. Ajout au groupe (un ajout répété n'est pas une erreur), puis lecture de `licenseAssignmentStates` (au plus 8 lectures, environ 30 s). Entrée `Active` : on continue (statut `Validé`, dossier). Entrée en erreur : le compte est **retiré du groupe**, puis 409 pour `CountViolation` (course entre deux validations), 502 avec `raison` pour les autres (`étape : licence_attribution`). Retrait impossible : 502 `licence_retrait_groupe`, à reprendre.
4. Pas d'entrée `Active` à l'issue des lectures : **202** `{ message: "Licence en cours d’attribution, revalidez dans une minute", code: "licence_en_cours", etape: "licence_verification" }` (ce n'est pas une erreur), statut inchangé, écran direction en avertissement, le compte **reste dans le groupe** ; rappeler `valider` le retrouve licencié et continue. Choix volontaire : le retirer ferait échouer en boucle un tenant dont le traitement dépasse 30 s.

L'écran direction affiche « Aucune licence disponible… » en évidence (bordure épaisse). Refuser un compte le supprime : la licence est libérée avec lui.

Traçabilité : `licence.groupe_ajout`, `licence.attribuee`, `licence.deja_attribuee`, `licence.indisponible` (avec `enabled` et `consumed`), `licence.refusee` (code d'erreur Entra), `licence.groupe_retrait`, `licence.verification_expiree` (dernière lecture : `lectures`, `entree`, `entrees`, `etat`, `erreur`, `parGroupe`, sans nom ni UPN), `licence.sku_introuvable`, `licence.non_choisie`, `licence.liste`, avec l'objectId du compte et les GUID du groupe et du SKU uniquement.

Terraform ([infra/licence.tf](infra/licence.tf)) : la variable `licenses` est une map `clé = { libelle, sku_id, group_id }`. Sans `group_id`, Terraform crée le groupe `sg-<nom>-licence-<clé>` (`azuread_group`) et lui attribue le SKU (`azuread_group_license`), en `prevent_destroy` (les détruire retire la licence de tous les comptes de ce SKU) ; avec `group_id`, il désigne un groupe existant et n'y pose rien (licence à poser dans le portail). `LICENSES` est généré à partir de la map ; l'extension `licenceOnboarding` est créée dans [infra/graph.tf](infra/graph.tf), comme `statutOnboarding`. Les membres ne sont pas déclarés dans Terraform : c'est l'app qui les ajoute. Dans le tenant de test il n'y a qu'un SKU (Business Premium) : le cas « SKU à 0 » n'y est couvert que par les tests unitaires.

## Activation, mot de passe temporaire et fin d'onboarding (étape 7)

Parcours de l'arrivant (réglages du tenant : [docs/reglages-tenant-onboarding.md](docs/reglages-tenant-onboarding.md), à faire à la main par un administrateur) : connexion avec l'adresse et le mot de passe temporaire (OOBE Autopilot en Entra join, ou n'importe quel service Microsoft), **inscription de Microsoft Authenticator imposée par l'accès conditionnel**, puis **changement du mot de passe imposé par Entra** (force d'authentification « Authenticator obligatoire » sur le groupe des arrivants). Le mot de passe posé à la création reste aléatoire, jamais stocké ni communiqué.

- `GET /api/activations` (droit `activer`, **lecture seule**) : comptes `Validé` (action `activer`, ou `attendre` avant la date d'arrivée) et **tous** les comptes `Actif` (action `regenerer`) tant que l'onboarding n'est pas `Terminé`, avec `onboarding: { motDePasse, authenticator, termine }` (`{ verification: "echec" }` si la lecture Graph d'un compte échoue : le reste de la liste n'est pas affecté). 1 000 comptes par statut au plus (10 pages de 100, `tronque`).
- `GET /api/suivi` (droit `acces` : RH ou Direction, **lecture seule**, pour l'écran de suivi) : `{ demandes, tronque }`, les demandes `EnAttente` (étape 1), `Validé` (2), `Actif` (3) et `Terminé` (4) dont l'**activation date de moins de 30 jours**, au plus **100 par statut** (`tronque` passe à `true` au-delà, ou si Graph tronque lui-même la liste). Par demande : `id`, `nom` (nom affiché), `upn` (adresse professionnelle, `userPrincipalName`, lue avec le reste dans la même requête Graph ; `null` si Graph ne la renvoie pas), `poste`, `service`, `dateArrivee`, `statut`, `etape`, `actions` et, pour `Actif` seulement, `onboarding` (même calcul qu'`activations` : `inspectOnboarding`, `{ verification: "echec" }` si la lecture d'un compte échoue). Ni manager, ni créateur. `GET /api/demandes` et `GET /api/activations` ne renvoient pas l'UPN (leur forme n'a pas changé). Aucune permission Graph nouvelle : `listByStatut`, `getOnboardingProgress` et `inspectOnboarding` existants, et le même 503 qu'`activations` si `ARRIVANTS_GROUP_ID` ou `ENTRA_ACTIVATION_EXTENSION` manque.
  - **`actions`**, calculé pour la personne connectée, que l'interface doit seul suivre : `["approuver", "refuser"]` si elle a le droit `approuver` et que la demande est `EnAttente` (y compris quand elle en est le créateur) ; `["activer"]` si elle a le droit `activer`, que la demande est `Validé` **et que le jour J est atteint** (date d'arrivée présente et au plus égale à aujourd'hui dans `TZ_METIER`, comme la route, qui répond 409 sinon) ; `["reprendre"]` si elle a le droit `approuver` et que la demande est `Validé` **sans dossier SharePoint** (une seule lecture de la racine de la bibliothèque pour toute la liste, seulement pour la direction ; lecture en échec, liste coupée ou nom impossible à former : pas d'action, jamais de reprise à l'aveugle ; aucune permission de plus) ; `["regenerer"]` si elle a le droit `activer` et que la demande est `Actif` (nouveau mot de passe temporaire ; l'onboarding terminé donne le statut `Terminé`, donc plus d'action) ; `[]` sinon, dont tous les `Terminé`. Ce sont exactement les actions que les routes acceptent (mêmes droits, mêmes statuts). Le créateur n'est ni lu ni renvoyé par cette route.
  - **Fenêtre des `Terminé`** : la date d'activation (extension `activationOnboarding`, à défaut création du compte pour un compte activé avant l'extension) n'est pas filtrable côté Graph (statut + date + `$expand` est refusé). Seuls les `Terminé` arrivés depuis moins de 90 jours (30 jours + 60 jours de délai possible entre l'arrivée et l'activation) sont lus un à un, puis filtrés sur l'activation : **un compte activé plus de 60 jours après sa date d'arrivée n'apparaît pas**. Tri de l'activation la plus récente à la plus ancienne. Une lecture en échec ne retire pas le compte de la liste (date inconnue, échec tracé `demande.echec`, étape `suivi_activation`).
  - Traçabilité : événement `suivi.liste` (objectId de l'acteur, nombre de résultats, `tronque`), jamais de nom ni d'UPN.
- `POST /api/demandes/:id/activer` (droit `activer`, corps `{}`) : 409 si le statut n'est pas `Validé` (`raison` : `deja_actif`, `onboarding_termine`, `statut`), si la date d'arrivée manque ou est dans le futur (comparée à « aujourd'hui » dans `TZ_METIER`, défaut `Europe/Paris`). Ensuite : `accountEnabled=true`, ajout au groupe des arrivants (déjà fait à la validation, rejoué sans effet), date de remise écrite dans l'extension `activationOnboarding`, mot de passe temporaire (`PATCH passwordProfile`, `forceChangePasswordNextSignIn: true`), puis statut `Actif`. Rejouable : après un échec le compte reste `Validé` et un nouvel « Activer » refait tout (le mot de passe déjà posé, jamais affiché, est remplacé).
- `POST /api/demandes/:id/regenerer` (droit `activer`, corps `{ "motif": "<code>" }`) : nouveau mot de passe temporaire (perdu, refusé). Le motif est **l'un de** `code_perdu`, `code_refuse`, `autre` et il est tracé tel quel (`demande.mdp_regenere`) ; pas de texte libre, qui pourrait contenir un nom (400 sinon). Comptes `Actif` activés seulement ; **409 une fois l'onboarding `Terminé`** (`onboarding_termine`). Remplace aussi un mot de passe déjà choisi par l'arrivant : il devra le changer de nouveau, et la référence repart de cette remise.
- `POST /api/demandes/:id/terminer` (droit `activer`, corps `{}`) : revérifie côté serveur (jamais sur la foi du client) que `lastPasswordChangeDateTime` est postérieur de **plus de 60 s** à la date de remise (la remise elle-même met à jour ce champ quelques secondes après ; repli sur la date de création du compte pour un compte activé avant l'extension) **et** qu'une méthode `microsoftAuthenticator` est inscrite, sinon 409 `onboarding_non_termine`. Puis : retrait du groupe des arrivants (seulement s'il en est encore membre : Graph répond 400 pour un non-membre), statut `Terminé` **en dernier**. Rejouable après un échec partiel. La route reste disponible (la tâche ci-dessous l'utilise) ; le nouvel écran `/app` ne l'appelle plus, l'ancienne page `/activation` l'appelle encore après chaque chargement.
- **Passage à Terminé : une tâche dans l'application** ([src/terminaison.ts](src/terminaison.ts)), démarrée par [src/server.ts](src/server.ts) : toutes les **5 minutes** (`TERMINAISON_INTERVAL_MS`, défaut 300000, `0` la désactive, 60000 au moins sinon ; premier passage 30 s après le démarrage ; le suivant n'est planifié qu'une fois le précédent fini), elle liste les comptes `Actif`, lit leur onboarding (comme `GET /api/suivi`) et passe à `Terminé` ceux dont il est complet, en réutilisant `terminerOnboarding` (qui revérifie chaque compte avant d'écrire). Un compte qu'une action de RH occupe (verrou en mémoire, partagé avec les routes) ou dont l'écriture échoue est laissé au passage suivant ; un échec n'arrête pas les autres comptes. Elle ne démarre pas sans `ARRIVANTS_GROUP_ID` et `ENTRA_ACTIVATION_EXTENSION`. **Pas de verrou partagé entre instances : POC à une seule instance App Service** (comme le verrou par compte). Avec plusieurs instances chacune ferait le passage : sans gravité (rejouable, un compte déjà `Terminé` est ignoré) mais les passages seraient doublés ; au-delà d'une instance, prévoir un verrou partagé (bail de blob) ou une tâche à part. **Traçabilité** : `onboarding.termine_auto` pour chaque passage (objectId du compte seulement, acteur `systeme:terminaison`), `onboarding.termine` et `onboarding.arrivants_retrait` de `terminerOnboarding`, et `terminaison.passage` (bilan `lus`, `termines`, `ignores`, ou l'erreur : code seulement) quand il s'est passé quelque chose. **Chaque passage** (même sans rien à faire) dépose en plus trois **mesures** Application Insights (table `customMetrics`, pas le journal d'audit) : `terminaison.lus`, `terminaison.termines` et `terminaison.ignores` ; pas de mesure pour un passage en erreur (l'événement d'erreur le dit). Elles disent que la tâche tourne et ce qu'elle a vu, sans bruit dans les événements. Aucune permission Graph de plus (mêmes écritures que `POST /terminer`) ; le compte reste `Actif` au plus 5 minutes après la fin réelle de l'onboarding.
- Réponse d'`activer` et de `regenerer` : `{ id, statut, regeneration, motDePasseTemporaire }` (format `Kp7m-Xq4r-Tz9w-Hb3n`, sans 0, O, 1, l ni I). Le mot de passe n'existe que dans cette réponse : jamais tracé, jamais stocké, `Cache-Control: no-store` sur toute l'API et sur les pages. L'interface l'affiche une seule fois et le garde dans le DOM uniquement (ni URL ni stockage navigateur). S'il est refusé juste après la remise, réessayer une à deux minutes plus tard (réplication).
- Échec d'une étape : 502 avec `etape` (`activation_compte`, `groupe_arrivants`, `activation_date`, `mot_de_passe`, `statut`), sans mot de passe dans la réponse ; RH relance la même action.
- Double clic : une seule action à la fois par compte (valider, refuser, activer, régénérer, terminer) et une création à la fois par personne RH ; la seconde reçoit 409 `action_en_cours`. Verrou en mémoire ([src/lock.ts](src/lock.ts)) : valable sur une seule instance App Service. L'interface désactive aussi les boutons pendant chaque écriture.
- `ARRIVANTS_GROUP_ID` ou `ENTRA_ACTIVATION_EXTENSION` absent : les quatre routes répondent 503 sans rien écrire.
- Terraform : groupe `sg-<nom>-arrivants` ([infra/arrivants.tf](infra/arrivants.tf), `prevent_destroy`) et extension `activationOnboarding` ([infra/graph.tf](infra/graph.tf)), injectés dans `ARRIVANTS_GROUP_ID` et `ENTRA_ACTIVATION_EXTENSION`. Les comptes `Actif` restent visibles jusqu'à `Terminé`.
- Prérequis tenant : paramètres de sécurité par défaut désactivés, Authenticator activé pour tous les utilisateurs, force d'authentification « Authenticator obligatoire » et accès conditionnel sur le groupe des arrivants. Sans l'accès conditionnel, le changement de mot de passe reste imposé mais pas Authenticator. Si l'activation échoue en 502 `mot_de_passe` avec `http: 403`, donner aussi le rôle **Password Administrator** à l'identité managée.

## Détail d'une demande et historique

- `GET /api/demandes/:id` (droit `acces` : RH ou Direction, **lecture seule**, `Cache-Control: no-store`) : tout ce que la page `/app/demandes/:id` affiche. `id` : objectId (GUID, sinon 400). **Garde-fou : 404 `Demande introuvable` pour un compte sans `statutOnboarding` valide** (ou inexistant) : sans cela, toute personne ayant accès lirait le profil de n'importe quel compte du tenant par son objectId. **Une demande refusée n'a pas de page** : refuser supprime le compte (corbeille Entra, 30 jours), l'historique du refus n'existe que dans le journal (`demande.refusee`).
  - Réponse : `id`, `nom`, `upn`, `poste`, `service`, `manager: { nom } | null`, `dateArrivee` (AAAA-MM-JJ), `statut`, `etape`, `licence: { libelle, etat } | null` (`choisie` avant la validation, puis `attribuee`, `en_cours`, `erreur` d'après `licenseAssignmentStates`, ou `inconnu`), `groupeArrivants: { membre } | null`, `dossier: { etat: 'present', url } | { etat: 'absent' } | null`, `onboarding` (comptes Actif, comme `GET /api/suivi`), `actions` (**mêmes règles que `GET /api/suivi`**, même fonction `actionsFor` : l'interface ne propose que celles-là ; `reprendre` seulement si la lecture du dossier a réussi et l'a trouvé absent) et `historique`.
  - **Aucune permission Graph de plus** : un `GET /users/{id}` avec `$expand=manager` (`User.Read.All`), le nom des auteurs par `GET /users/{id}` (`User.Read.All`, au plus trois appels ; un auteur dont le compte n'existe plus donne `nom: null`), `microsoftAuthenticatorMethods` (`UserAuthMethod-MicrosoftAuthApp.Read.All`, **seule la date est gardée, jamais le nom de l'appareil**), `checkMemberGroups` (`GroupMember.ReadWrite.All`), `licenseAssignmentStates` (`User.Read.All`) et `GET root:/{nom}` du dossier (`Sites.Selected`). Une lecture annexe qui échoue est tracée (`demande.echec`, étape `detail_*`) et ne fait pas échouer la page (rubrique `null` ou `inconnu`). Événement `demande.detail` (objectIds, statut), jamais de nom.
  - **`historique`** : `enregistre` (faux : extensions d'historique non configurées), `creation: { le, par }` (`createdDateTime` d'Entra et créateur, `createurOnboarding`), `validation`, `activation`, `regeneration` (dernière, avec `nombre` de remises depuis l'activation), `termine` : `{ le, par: { nom, systeme? } }` ou `null` ; `authenticator: { le } | null` ; `motDePasse: { le } | null`. Les dates sont en UTC (ISO) ; l'interface les affiche en heure de Paris. `null` pour une étape faite avant l'historique : l'interface le dit (« non enregistrée »), rien n'est inventé.
  - **Date d'inscription d'Authenticator** : `createdDateTime` d'une méthode `microsoftAuthenticator` est **nulle quand l'appareil n'est pas inscrit à la connexion sans mot de passe** (doc Graph v1.0) : `authenticator: { le: null }` signifie « inscrit, date non fournie par Entra ».
- **Écriture de l'historique** : quatre extensions Entra de type chaîne, `validationOnboarding`, `premiereActivationOnboarding`, `regenerationOnboarding`, `termineOnboarding` ([infra/graph.tf](infra/graph.tf), `prevent_destroy`, injectées dans `ENTRA_HISTORY_VALIDATION_EXTENSION`, `ENTRA_HISTORY_ACTIVATION_EXTENSION`, `ENTRA_HISTORY_REGENERATION_EXTENSION`, `ENTRA_HISTORY_TERMINE_EXTENSION`). Valeur `<objectId de l'auteur>|<date ISO UTC>` (régénération : `…|<nombre>`), 65 caractères au plus pour les 256 d'une extension ; l'auteur de la tâche de terminaison est `systeme`. Chaque valeur est écrite **dans le même PATCH que le statut** (`Validé`, `Actif`, `Terminé` : jamais un statut sans son auteur) ; la régénération est écrite avec la date de remise, **avant** le mot de passe (une écriture après lui qui échouerait ferait répondre 502 alors que le mot de passe est déjà posé). Une reprise de `valider` ne réécrit pas la validation ; une régénération n'écrase pas l'activation (extension à part) ni `activationOnboarding`, dont le format (date seule) reste celui que lit `inspectOnboarding`. **Les quatre ou aucune** (`loadConfig` refuse un réglage partiel) ; **sans elles, rien n'est écrit en plus et aucune route ne répond 503** (déployer avant d'appliquer Terraform reste sans danger : l'historique démarre à l'apply). Pas de rattrapage : les comptes validés ou activés avant l'apply n'ont pas ces étapes.

## Easy Auth (Entra)

Terraform ([infra/entra.tf](infra/entra.tf), [infra/main.tf](infra/main.tf)) crée tout, sans secret ni jeton d'accès implicite (les ID tokens sont activés : Easy Auth exige le flux hybride) :

- l'inscription d'application, avec les rôles d'application `RH` et `Direction`, et son service principal (`app_role_assignment_required` : seuls les utilisateurs affectés à un rôle se connectent) ;
- un **credential fédéré** : l'identité managée de la Web App (émetteur `https://login.microsoftonline.com/<tenant>/v2.0`, sujet = objectId de l'identité, audience `api://AzureADTokenExchange`) remplace le secret client ;
- `authsettingsV2` : authentification obligatoire sauf `/healthz`, flux hybride `code id_token` (forcer `response_type=code` donne un 401 au callback : « no 'id_token' »), `client_secret_setting_name = OVERRIDE_USE_MI_FIC_ASSERTION_CLIENTID`, ce réglage d'application contenant le client ID de l'identité managée (pas celui de l'inscription), comme le décrit la documentation App Service.

Les rôles s'affectent par `rh_principal_object_ids` et `direction_principal_object_ids` (fichiers `envs/*.tfvars`, objectIds d'utilisateurs ou de groupes) ou dans le portail Entra. **Tout porteur du rôle Direction peut créer, valider et refuser des demandes (sauf les siennes)** : l'affectation du rôle est la seule désignation de la direction. Sur test et dev, `directeur@` porte le rôle Direction par `direction_principal_object_ids` (avant, par la variable `direction_object_id`, supprimée avec `direction_type` : leur nom suggérait un valideur désigné, qui n'existe plus ; les affectations de rôle sont inchangées, `terraform plan` ne doit montrer aucune modification de `azuread_app_role_assignment`). `app_role_assignment_required` refuse à la connexion toute personne sans rôle.

Si un rôle est affecté à un **groupe** : l'affectation d'un rôle à un groupe exige Entra ID P1, et seuls les **membres directs** reçoivent le rôle (le jeton d'un membre d'un sous-groupe n'en porte pas) ; l'ajouter directement au groupe ou à `direction_principal_object_ids`.

L'identité managée sert à la fois d'assertion Easy Auth et d'identité d'appel à Graph : ne l'affecter à aucune autre ressource.

## Permissions Microsoft Graph

Application permissions accordées par Terraform ([infra/graph.tf](infra/graph.tf), `azuread_app_role_assignment`) à l'identité managée de l'App Service (suppression d'un compte : couverte par `User.ReadWrite.All`). Aucun secret : sur App Service (`IDENTITY_ENDPOINT` présent), l'app utilise `ManagedIdentityCredential` visé sur `AZURE_CLIENT_ID` (démarrage refusé s'il manque) ; en local, `DefaultAzureCredential` (`az login`).

| Permission | Pourquoi |
| --- | --- |
| `User.ReadWrite.All` | Créer le compte désactivé, écrire ses attributs et `statutOnboarding`, puis l'activer. |
| `User.Read.All` | Résoudre le manager et vérifier la disponibilité de l'email (UPN/mail) avant création. |
| `User-PasswordProfile.ReadWrite.All` | Poser le mot de passe temporaire le jour J (`PATCH /users/{id}` avec `passwordProfile`, `forceChangePasswordNextSignIn: true`) à l'activation et à la régénération. Plus étroite que `User.ReadWrite.All` pour ce champ, et remplace `UserAuthenticationMethod.ReadWrite.All` et `UserAuthMethod-TAP.ReadWrite.All` (retirées). Si Graph répond 403, ajouter le rôle d'annuaire **Password Administrator**, qui ne permet de réinitialiser que les comptes non administrateurs. **Sensible** : poser un mot de passe permet de prendre un compte. Garde-fous dans l'app : seulement sur un compte au statut `Validé` (jour J atteint) ou `Actif` non terminé, rôle RH, chaque remise tracée (objectIds, jamais le mot de passe). **Limite connue** : le statut est une extension que tout administrateur d'utilisateurs peut écrire ; avant la prod, restreindre l'app (unité administrative à gestion restreinte, ou refus des comptes ayant un rôle d'annuaire). |
| `UserAuthMethod-MicrosoftAuthApp.Read.All` | Lire les méthodes Microsoft Authenticator (`GET /authentication/microsoftAuthenticatorMethods`) pour décider que l'onboarding est terminé. Lecture seule, limitée à cette méthode. |
| `Sites.Selected` | Accès limité à **un seul** site SharePoint : créer les dossiers dans la bibliothèque `SHAREPOINT_DRIVE_ID`. Le grant explicite (rôle `write`, `POST /sites/{id}/permissions`) est posé par Terraform sur `sharepoint_site_id`, ou à la main si `manage_sharepoint_grant = false` (voir ci-dessous). |
| `GroupMember.ReadWrite.All` | Ajouter le compte au groupe de licence à la validation (retrait en cas de `CountViolation`), et au groupe des arrivants à la validation (retrait à `Terminé`). Couvre aussi `checkMemberGroups` (appartenance au groupe des arrivants, à la finalisation), ce qui remplace `GroupMember.Read.All`. **Sensible** : permet d'ajouter n'importe quel compte à n'importe quel groupe de sécurité du tenant qui n'est pas assignable à un rôle (donc d'en hériter les accès). Un groupe assignable à un rôle resterait inaccessible (il exigerait `RoleManagement.ReadWrite.Directory`, volontairement non accordée). |

C'est le moindre privilège de cette route ; `Organization.Read.All` (plus large) n'est pas nécessaire. #### Grant SharePoint : géré par Terraform ou posé à la main

La variable `manage_sharepoint_grant` (défaut `true`) décide qui pose le grant `write` du site :

- `true` : Terraform le crée via `msgraph`. L'identité d'apply doit avoir `Sites.FullControl.All`.
- `false` : Terraform ne gère pas le grant. À utiliser quand l'apply tourne avec un jeton qui n'a pas ce droit (par exemple `az login`, dont le jeton n'a aucun scope `Sites.*` : l'erreur est un 403 `accessDenied`). Poser alors le grant une fois, avec un compte administrateur ayant consenti `Sites.FullControl.All` (Graph Explorer, par exemple) :

  `POST https://graph.microsoft.com/v1.0/sites/{sharepoint_site_id}/permissions`, corps `{"roles": ["write"], "grantedToIdentities": [{"application": {"id": "<managed_identity_client_id>", "displayName": "<nom de l'identité managée>"}}]}`

  `managed_identity_client_id` est une sortie Terraform. Vérifier ensuite avec `GET /sites/{id}/permissions`. Le grant n'est pas dans l'état Terraform : il survit à un `destroy` et doit être retiré à la main (`DELETE /sites/{id}/permissions/{permission-id}`).

L'environnement `test` utilise `false` ([envs/test.tfvars](infra/envs/test.tfvars)).

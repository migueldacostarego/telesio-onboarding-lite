## Étape 1 : Approuver / Refuser

- **Pas de champ « compte prêt » dans `GET /api/suivi`.** Le bouton Valider ne peut donc pas être désactivé d'avance (CLAUDE.md le souhaitait). Le seul signal est le **404 `Demande introuvable`** de `POST /valider`, renvoyé par `loadForAction` avant toute écriture. Je l'ai traité comme « compte en cours de création » : message dans la ligne, ligne verrouillée, **nouvel essai automatique** à 5, 5, 10, 10, 15 et 15 s (6 essais, environ une minute). Passé ce plafond, l'erreur s'affiche avec `ApiErrorAlert` et les boutons sont rendus : un compte réellement supprimé donne aussi 404, il ne faut pas boucler.
  - Exception assumée à « une écriture n'est jamais rejouée » : elle est sûre (rien n'a été écrit), bornée, et annulée si la demande disparaît de la liste ou n'offre plus `approuver`.
  - `refuser` n'est **jamais** rejoué sur un 404 (c'est une suppression) : l'erreur s'affiche.
  - Alternative écartée : ajouter côté API un champ de disponibilité (une lecture Graph de plus par demande, hors périmètre).
- **202 `licence_en_cours`** : « Licence en cours d'attribution », revalidation automatique après 60 s, **5 fois au plus**, puis un avertissement (pas une erreur) et la main rendue. Même annulation que ci-dessus.
- **État de chaque ligne au niveau de la page** (`useActionsDemandes`), par id : la recherche, le filtre ou le passage tableau / cartes démontent les lignes sans perdre le spinner, ni un nouvel essai planifié, ni une erreur, et sans permettre un second clic. Le serveur garde en plus son verrou (409 `action_en_cours`).
- **Une session expirée** (401 ou réponse hors JSON) sur une écriture passe par la `MutationCache` de `query.ts` : écran de reconnexion, aucune erreur de ligne.
- **Erreurs** (403 `droit_manquant`, 409, 502 avec `etape` ; le 403 `auto_approbation` n'existe plus, voir « Changements de règle ») : `ApiErrorAlert` sous la ligne (tableau) ou dans la carte (mobile), avec « Fermer ce message ». Elles restent jusqu'à fermeture ou nouvelle tentative, même si la liste change entre-temps. La liste est relue après chaque erreur (la demande a pu être traitée ailleurs, ou une reprise partielle avoir eu lieu).
- **Refuser** : boîte de dialogue, motif obligatoire (espaces seuls refusés, 500 caractères au plus, limite de l'API), bouton « Confirmer le refus ». Pendant l'attente la boîte ne se ferme ni par Échap, ni par Annuler. À la réponse elle se ferme, et une éventuelle erreur est dans la ligne (le motif saisi est perdu : il n'est conservé nulle part). La boîte se ferme aussi si la demande ne se refuse plus (traitée ailleurs).
- **Reprise du dossier SharePoint après un 502 : action `reprendre` (ajoutée ensuite, voir plus bas « Corrections demandées après coup »).** Version précédente de cette session : lacune signalée, aucune action pour la direction sur un compte `Validé` ; corrigée.
- **Journal du navigateur** : Chrome écrit « Failed to load resource » pour chaque réponse HTTP non 2xx (404, 409, 502 des scénarios de contrôle). Ce n'est pas un message de la console de l'application (0 `console.error`, 0 exception, 0 violation CSP) et aucun code ne peut le supprimer.

## Étape 2 : Activer, mot de passe temporaire, Régénérer, passage à Terminé

- **Le serveur propose maintenant `regenerer`** dans `actions` de `GET /api/suivi` (droit `activer`, compte `Actif`). Sans cela, `actions` valait `[]` pour tous les `Actif` et l'interface n'aurait pas pu offrir Régénérer en suivant la règle « seulement ce que propose `actions` ». Changement dans `src/suivi.ts`, testé (`test/droits.test.ts`), aucune permission Graph de plus, aucun appel de plus. À relire : c'est la seule modification de l'API faite pendant cette session.
- **Activer n'est proposé qu'à partir de la date d'arrivée, et c'est le serveur qui le décide.** `GET /api/suivi` ne met `activer` dans `actions` que si le jour J est atteint (jour calculé dans `TZ_METIER`, comme la route `activer`) ; une date d'arrivée absente ou à venir n'ouvre rien. L'écran suit `actions` et ne calcule aucune date : il n'utilise pas l'horloge du navigateur, qui peut différer du fuseau métier. (Version précédente de cette session : le bouton était proposé avant le jour J et le serveur répondait 409 ; corrigé.)
- **Le mot de passe temporaire n'existe que dans le DOM de la boîte et dans l'état React de la page.**
  - L'écriture `activer` / `regenerer` est une mutation construite **sans observateur** (`getMutationCache().build(...).execute`) : `useMutation` aurait gardé la dernière réponse dans son résultat. Avec `gcTime: 0`, elle quitte le cache dès qu'elle se termine.
  - Vérifié par des tests (cache des mutations et des requêtes, `localStorage`, `sessionStorage`, adresse, titre, requêtes sortantes, console) et dans Chrome (stockage vide, adresse inchangée, texte absent du HTML après la fermeture).
  - **Copier** écrit dans le presse-papiers du système, sur clic explicite : l'application ne peut pas l'en retirer ensuite. Une copie impossible est annoncée.
- **La boîte du mot de passe ne se ferme ni par Échap ni par un clic à côté** (un mot de passe affiché une seule fois ne doit pas se perdre par accident), seulement par « Fermer ». Elle n'a pas de croix. Une seule boîte à la fois : la confirmation cède la place au mot de passe dans le même rendu.
- **Activer et Régénérer ne sont jamais rejoués** par l'interface (un nouveau mot de passe remplacerait le précédent). Une erreur 409 ou 502 s'affiche dans la ligne, la personne relance.
- **Régénérer** : le motif est un choix parmi les trois codes de l'API (`code_perdu`, `code_refuse`, `autre`), en boutons radio, pas du texte libre (l'API le refuse en 400). Le texte de la confirmation prévient que l'ancien mot de passe ne fonctionne plus.
- **Passage à Terminé : version précédente de cette session (remplacée, voir « Corrections demandées après coup », point 3).** L'écran appelait `POST /terminer` après chaque lecture de la liste (`useTerminaisonAuto`) ; retiré : c'est maintenant une tâche du serveur.
- **Test serveur instable constaté une fois** : `test/direction.test.ts` « 409 sans suppression… » a échoué une fois pendant que d'autres commandes tournaient en parallèle, puis a passé 4 fois de suite (et sur le code d'avant mes changements). Non lié à cette étape ; à surveiller en CI.

## Corrections demandées après coup

### 1. Activer n'est proposé qu'à partir de la date d'arrivée
Fait côté serveur (voir l'étape 2 ci-dessus, bullet corrigé) : `GET /api/suivi` ne met `activer` dans `actions` que si le jour J est atteint dans `TZ_METIER`, comme la route. L'écran suit `actions`, sans calcul de date.

### 2. `reprendre` : recréer le dossier SharePoint manquant
- **Route** `POST /api/demandes/:id/reprendre` (droit `approuver`, corps `{}`) : sur un compte `Validé` seulement (409 sinon), recrée le dossier SharePoint (idempotent : un dossier déjà là est réutilisé) **sans** refaire la licence, ni le groupe des arrivants, ni le statut. Une seule écriture Graph. 503 sans SharePoint, 502 avec `etape` (`dossier_sharepoint`) si SharePoint échoue, 409 `action_en_cours` si un appel est déjà en cours sur le compte. Tracée : `demande.dossier` puis `demande.reprise_dossier` (objectId de l'acteur et du compte, jamais le nom ni l'URL du dossier).
- **Qui reçoit l'action.** `GET /api/suivi` met `reprendre` dans `actions` pour la personne qui a le droit `approuver` quand un compte `Validé` n'a pas son dossier. **Choix :** tout porteur du droit `approuver` la reçoit, créateur compris (reprendre n'approuve rien, la validation a déjà eu lieu ; aucune trace d'auto-approbation).
- **Comment on sait que le dossier manque.** Une seule lecture de la racine de la bibliothèque (`GET …/root/children`, pages de 999, 10 au plus), pas une par compte, seulement pour la direction et seulement s'il y a des comptes `Validé`. Le nom attendu est calculé comme à la validation (`SHAREPOINT_FOLDER_PATTERN`, prénom et nom lus avec la liste, jamais renvoyés), comparé sans tenir compte de la casse. **Aucune permission de plus** (la lecture est couverte par le droit `write` du site, `Sites.Selected`).
- **Prudence.** Lecture en échec, liste coupée au plafond de pages ou nom impossible à former : **aucune action proposée** (jamais de reprise à l'aveugle) ; l'échec est tracé (`demande.echec`, étape `suivi_dossiers`). Limite connue : si `SHAREPOINT_FOLDER_PATTERN` change après la validation, les comptes déjà validés sous l'ancien nom auront `reprendre` (le dossier sous le nouveau nom serait créé en double). À ne pas changer en cours de route.
- **Écran.** Bouton « Réessayer » (nom accessible « Réessayer la création du dossier de … ») sur la ligne et dans le détail, sans boîte de dialogue (rien de destructif, pas de secret), le spinner remplace l'icône (le libellé du bouton ne change plus pendant l'action : « Nouvelle tentative… » est dit aux lecteurs d'écran à part, voir « Mise en page du tableau »), ligne verrouillée, **jamais rejoué tout seul**. Dans le détail, l'étape Validée est « en échec : le dossier SharePoint n'a pas été créé » tant que `reprendre` est proposé.

### 3. Le passage à Terminé se fait côté serveur
- **Une tâche dans l'application** (`src/terminaison.ts`, démarrée par `src/server.ts`), **toutes les 5 minutes** : liste les comptes `Actif`, lit leur onboarding, et termine (`terminerOnboarding`, qui revérifie chaque compte avant d'écrire) ceux dont l'onboarding est complet. Premier passage 30 s après le démarrage ; le suivant n'est planifié qu'une fois le précédent fini (jamais deux passages en même temps). `TERMINAISON_INTERVAL_MS` règle la période (défaut 300000, `0` désactive, 60000 au moins) ; `infra/` n'est pas modifié (le défaut convient), rien n'a été déployé.
- **Pas de verrou partagé entre instances : POC à une seule instance App Service.** Même limite que le verrou par compte (`KeyedLock`, en mémoire). Les routes et la tâche partagent **le même verrou en mémoire** : une action de RH sur un compte fait passer la tâche son tour pour ce compte. Avec plusieurs instances, chacune ferait la tâche : sans gravité (rejouable, un compte déjà `Terminé` est ignoré), mais des passages doublés. À traiter si l'application passe à plusieurs instances.
- **L'écran n'appelle plus `terminer`** (`useTerminaisonAuto` supprimé, test qui vérifie qu'aucune écriture ne part même quand l'API dit « complet »). `POST /api/demandes/:id/terminer` reste disponible ; plus aucune page ne l'appelle (l'ancienne page `/activation`, qui le faisait, est retirée).
- **Conséquence visible** : un compte reste « Activée » jusqu'à 5 minutes après la fin réelle de l'onboarding (plus la période d'actualisation de l'écran, 30 s). Avant, l'écran le terminait à la lecture suivante.
- **Traçabilité (objectId seulement)** : `onboarding.termine_auto` pour chaque passage à Terminé (acteur `systeme:terminaison`, cible = objectId du compte), `onboarding.termine` et `onboarding.arrivants_retrait` (déjà émis par `terminerOnboarding`), `terminaison.passage` avec le bilan (`lus`, `termines`, `ignores`) ou l'erreur (code seulement), émis seulement quand il s'est passé quelque chose. **Ajout (recette sur test)** : chaque passage terminé dépose aussi les mesures `terminaison.lus`, `terminaison.termines`, `terminaison.ignores` (`customMetrics`, via `Audit.metric`), pour prouver que la tâche tourne sans ajouter d'événement toutes les 5 minutes ; aucune mesure pour un passage en erreur. Testé : aucun nom, UPN ni domaine dans le journal.
- **Pas de permission de plus** : mêmes lectures et mêmes écritures Graph que `POST /terminer`. La tâche ne démarre pas sans `ARRIVANTS_GROUP_ID` et `ENTRA_ACTIVATION_EXTENSION`.

## Changements de règle

### Direction a tous les droits de RH, plus approuver
`droitsDe` : **Direction** donne `creer`, `approuver` et `activer` (RH donne `creer` et `activer`). La personne de la direction peut donc aussi activer un compte, régénérer le mot de passe, terminer et lire la liste des activations ; `GET /api/suivi` lui propose `activer` (jour J atteint) et `regenerer`, en plus de `approuver`, `refuser` et `reprendre`. L'écran n'a pas changé : il suit `droits` et `actions`. Les routes d'activation refusent toujours (403 `droit_manquant`) un rôle étranger ou l'absence de rôle.

### L'auto-approbation est autorisée, et tracée
- **Supprimés** : le 403 `auto_approbation` de `valider` et `refuser`, et l'exclusion du créateur dans les `actions` de `GET /api/suivi`. Le créateur d'une demande voit `Valider` et `Refuser` comme le reste de la direction.
- **Gardés** : l'extension `createurOnboarding` (écrite à la création, 503 sans `ENTRA_CREATOR_EXTENSION` pour créer, valider et refuser) et la lecture du créateur dans `valider` et `refuser`.
- **Trace** : `demande.auto_approbation` (`outcome: ok`, objectId de l'acteur, objectId du compte, `operation`) à chaque `valider` ou `refuser` par le créateur, objectIds seulement (testé : ni nom ni motif). **Choix :** l'événement est émis une fois le statut contrôlé (un 409 n'est pas une approbation) et avant les écritures ; si la validation échoue ensuite (licence, Graph), la trace existe quand même, et la tentative est visible à côté dans `demande.echec`. `reprendre` n'en émet pas.
- **Simplification** : `GET /api/suivi` ne lit plus le créateur dans Graph (plus de `$select` de l'extension ni de 503 sans elle), `PendingDemande.createur` et le paramètre `creatorExt` de `listByStatut` sont retirés.
- **Conséquence** : la séparation des tâches n'est plus imposée par l'application ; elle ne repose plus que sur la lecture de `demande.auto_approbation` dans Application Insights.

### La ligne ne disparaît plus après une action (réplication d'Entra)
- **Bug vu sur test** : après Valider, la ligne disparaissait jusqu'au rechargement : la recherche par statut de Graph (`GET /api/suivi`) ne voit pas tout de suite le compte à son nouveau statut.
- **Correction** (`lib/synchro.ts`) : après **créer, valider et activer**, la ligne est écrite dans le cache avec le nouveau statut, `actions` vide (sauf une demande créée : `approuver` et `refuser` si le droit `approuver`) et `synchro: true`. Chaque lecture de l'API est **fusionnée** avec ces lignes (dans le `queryFn`, donc le cache ne contient jamais la liste « en retard ») : l'API plus ancienne ne fait pas revenir la ligne en arrière, l'API qui ne renvoie pas la ligne ne la fait pas disparaître. Elle redevient celle de l'API dès que celle-ci la rend au statut attendu ou plus avancé, ou **au bout de 3 minutes** (la ligne disparaît alors si l'API ne l'a toujours pas, et la liste est relue à l'échéance).
- **Indicateur** « synchronisation… » (petit spinner, `role="status"`) sur la ligne, tableau et cartes, pas dans le panneau de détail. La liste est relue toutes les 5 s tant qu'une ligne est en attente (la relecture « 6 fois puis abandon » de la création est remplacée par cette règle commune).
- **Choix** : refuser retire la ligne comme avant, sans la garder ; si l'API la renvoie encore un instant (compte supprimé pas encore répliqué), elle peut réapparaître jusqu'à la relecture suivante. Régénérer et reprendre ne changent pas de statut : rien à garder. Après activer, `onboarding` est posé à « rien de fait » (vrai à l'instant de l'activation) jusqu'à la lecture de l'API.
- Le mot de passe temporaire n'entre jamais dans la ligne mise en cache (testé).

### Mise en page du tableau
- Cause : `table-layout: auto` calcule les largeurs d'après le contenu. Mesuré dans Chrome (fenêtre de 1 280 px, 990 px de contenu) : le tableau passait de 990 à 1 730 px selon les textes, puis à 1 739, 1 758 et 1 820 px au fil de la validation (bouton « Validation… », « synchronisation… », deux boutons), et les colonnes bougeaient à chaque fois (5 jeux de largeurs différents).

Mesuré après : 990 px dans tous les états, **un seul jeu de largeurs**, 72 px pour toutes les lignes, aucun débordement dans les colonnes Arrivée à Actions.
- **Choix** : le libellé d'un bouton ne change plus pendant l'action (« Valider » reste « Valider », le spinner remplace l'icône ; « Validation… » est dit aux lecteurs d'écran dans une zone `status`). Sinon la largeur du bouton change (« Nouvelle tentative… » est bien plus long que « Réessayer ») et la colonne Actions devrait être beaucoup plus large. Ce que voit la personne : le spinner et le bouton grisé. Dans le tableau, deux boutons au plus tiennent sur une ligne dans la colonne Actions.
- `scrollbar-gutter: stable` sur la page : l'apparition de la barre de défilement (liste longue, puis filtre) ne change plus la largeur du contenu. Non mesurable dans Chrome sans interface (barres masquées) : à vérifier sur un vrai navigateur.
- Cartes mobiles : non modifiées (hauteur variable par nature).

### Compteurs
- **« Terminées » = terminées ce mois-ci, calendrier de Paris** (demandé après la première version, qui comptait « 30 derniers jours »). `GET /api/suivi` lit `termineOnboarding` dans le `$select` de la requête des Terminé (aucune requête de plus, aucune permission) et renvoie seulement `termineCeMois` (booléen ou `null`). Mois calculé dans `TZ_METIER` (Paris par défaut), testé à la limite (30 sept. 22:30 UTC = 1er oct. à Paris).
  - **Comptes terminés avant l'historique** (pas de date de fin) : activés ce mois-ci, ils sont terminés ce mois-ci (la fin suit l'activation) ; activés plus tôt, **le mois est inconnu** (`null`) : non comptés, et le compteur affiche « + » (« au moins ») tant qu'il y en a. Le « + » disparaît quand ces comptes sortent de la fenêtre de 30 jours, au plus un mois après l'apply Terraform.
  - **Le filtre « Terminées » montre ce mois et les inconnues**, pas le mois dernier : un nombre `n+` peut donc être inférieur au nombre de lignes. Une Terminée du mois dernier reste visible dans « Toutes » (fenêtre de 30 jours d'activation inchangée) mais n'a plus de groupe : la somme des compteurs peut être inférieure au total.
  - **La fenêtre s'élargit d'un cas** : un compte terminé ce mois-ci est listé même activé il y a plus de 30 jours (onboarding long), sinon il manquerait au compteur.
- **« À activer »** = Validée dont l'API propose `activer` (jour J atteint, calculé par le serveur). Un compte validé dont la date manque, ou une ligne qui attend la réplication d'Entra (actions vides), tombe provisoirement dans « En cours ». Ce n'est pas « aujourd'hui » strictement : les arrivées passées non activées y restent (c'est voulu : elles sont en retard).
- **Les compteurs remplacent le filtre par statut** : on ne peut plus isoler Validée de Activée seules (« En cours » les réunit, le badge les distingue). Un seul jeu de commandes, pas deux filtres qui se recouvrent.
- Liste tronquée : nombres affichés avec « + ».
- « Aujourd'hui » et le tri utilisent maintenant **le jour à Paris** (`jourAParis`), plus celui du navigateur : cohérent avec le serveur. Hors Paris, `TZ_METIER` différent de Europe/Paris ferait diverger l'écran du serveur : l'heure de Paris est écrite en dur dans `lib/dates.ts`, comme demandé.

### Menu « … » et action principale
- **Une action principale par ligne** : Valider, à défaut Activer, à défaut Réessayer (dossier). Quand un compte Validé a à la fois `activer` et `reprendre`, **Activer est principal** (le jour J ne s'attend pas) et « Dossier SharePoint à refaire » est en rouge dans la ligne ; Réessayer est dans le menu. Les autres actions (Refuser, Régénérer) et « Voir le détail » sont dans le menu. Les noms accessibles ne changent pas (« Refuser la demande de … »).
- **Bug trouvé par les tests et corrigé :** un clic sur une entrée du menu « … » remontait (les événements React traversent les portails) jusqu'à la ligne et ouvrait la page de détail. `ouvrirSiLigne` ignore désormais les clics hors du DOM de la ligne et les éléments `menu` / `menuitem` ; test de non-régression.
- Le bouton principal garde sa largeur (`min-w`) et sa hauteur : rien ne bouge pendant l'action.

### Page de détail `/app/demandes/:id`
- **L'adresse ne porte que l'objectId.** Navigation par `<Link>` sans `state` : l'historique du navigateur ne conserve ni nom ni UPN (testé : `history.state` vide). Un lien profond se recharge par le vrai routeur Express (vérifié dans Chrome).
- **État partagé au-dessus des routes** (`FournisseurDemandes`) : liste, `useActionsDemandes`, boîtes de dialogue et boîte du mot de passe. Naviguer liste ↔ détail ne perd ni spinner, ni nouvel essai planifié, ni erreur de ligne, ni la boîte du mot de passe, et ne permet pas de second clic. Recherche, filtre et tri aussi (mémoire seulement). Le mot de passe reste dans l'état React du fournisseur : toujours ni URL, ni stockage, ni cache (tests repris).
- **Les boutons d'action de la page viennent de la ligne de `GET /api/suivi`**, pas de `actions` du détail (même fonction serveur, mêmes valeurs ; la ligne porte en plus la synchronisation d'Entra). Sans la ligne (lien vers une demande hors liste, par exemple une Terminée de plus de 30 jours), la page est en lecture seule. L'étape affichée est la plus avancée des deux sources.

- Chronologie : une étape faite sans date enregistrée dit « Date non enregistrée », un auteur supprimé « un compte supprimé », la tâche du serveur « le serveur (automatiquement) », une inscription Authenticator sans date « Date non fournie par Entra ». Jamais une valeur inventée. Heures de Paris (`Intl`, `timeZone: 'Europe/Paris'`, testé sous quatre fuseaux de navigateur et aux passages à l'heure d'été et d'hiver) ; les dates d'arrivée (AAAA-MM-JJ) ne passent jamais par un fuseau.

## Formulaire « Nouvelle demande » par type de contrat (session du 2026-10-30)

Demande : fenêtre modale à trois sections, email pro proposé et vérifié, plus de choix de licence (le type la détermine), type affiché dans la liste et le détail. Choix faits en cours de route, à relire :

- **Nom du champ : `typeContrat`**, valeurs **`"Employé"` et `"Contractor"`**, les mêmes dans le corps de l'API, dans `employeeType` et à l'écran (comme les statuts `Validé`, `Terminé` : pas de code à traduire). Une valeur d'`employeeType` hors de ces deux-là (compte créé ailleurs) est lue comme `null`, jamais affichée.
- **La licence n'est plus un champ, et l'envoyer est une erreur** (400 `details.licence`) plutôt que d'être ignoré : un client qui croit choisir une licence ne doit pas la voir remplacée en silence. Conséquence : l'ancienne page `/demande` avait été adaptée (menu « Type de contrat » à la place de la licence), sinon chaque envoi aurait été refusé ; elle est retirée depuis, avec `GET /api/licences`.
- **Mapping `LICENCES_PAR_TYPE` (env), validé au démarrage, mais absent = 503 à la création, pas un arrêt.** Chaque type est **facultatif** : un type sans licence (absent ou `null`) n'est pas une erreur de configuration mais un refus **409 « Aucune licence disponible pour ce type de contrat »** (même `code: licence_indisponible` qu'une licence épuisée, donc même message sous le type de contrat, et même tracé `licence.indisponible` avec `raison: non_prevue`). Ce 409 est rendu avant toute lecture Graph. Les types configurés visent des SKU de `LICENSES` (la validation a besoin du groupe). Distinction voulue : variable absente = pas encore déployée (503) ; variable présente mais type sans licence = décision (409). Absent n'arrête pas l'application : dev se déploie à chaque fusion sur `main`, et un code déployé avant l'apply Terraform ne doit pas la faire tomber. Terraform : `license_by_type` (clés de `licenses`).
- **`licenceOnboarding` reste écrite** avec la licence dérivée : `valider`, le détail et la reprise ne changent pas, et un compte créé avant le type garde sa licence d'origine.
- **Email : champ facultatif côté API.** Fourni : c'est l'UPN, **une seule tentative** (pris : 409 `email_pris`, jamais de suffixe ajouté en silence, parce que c'est l'adresse que la personne recevra). Absent : l'ancien comportement (UPN généré, suffixe 2, 3…), que les pages actuelles utilisent encore. Le formulaire envoie toujours l'adresse.
- **Les homonymes changent de comportement dans le formulaire** : avant, « Anna Martin » devenait `anna.martin2` sans rien dire ; maintenant la proposition `anna.martin` s'affiche « Adresse déjà utilisée » et il faut la modifier (ajouter un chiffre, un second prénom). Voulu : l'adresse est visible avant l'envoi. Pas de suggestion automatique d'une variante libre (elle demanderait plusieurs appels de vérification par frappe).
- **Vérification de disponibilité : nouvelle route `POST /api/annuaire/disponibilite`** (aucune n'existait ; `upnTaken` n'était pas exposée). Corps JSON, pas d'URL (pas de PII), adresse jamais tracée. Une adresse connue comme prise **bloque** l'envoi ; une vérification en échec **ne le bloque pas** (le serveur revérifie et répond 409). Une réponse arrive 400 ms après la dernière frappe, et une adresse mal formée n'appelle rien.
- **Le domaine des adresses vient de `GET /api/moi` (`domaine`).** Le navigateur ne le connaissait pas ; `/api/moi` est déjà lu au chargement et mis en cache, donc aucun appel de plus. Sans domaine (serveur plus ancien), le formulaire affiche « Chargement… » puis un message, plutôt que de proposer une adresse sans domaine.
- **La proposition recopie `normalizePart` du serveur** (`lib/email.ts`), avec les mêmes cas des deux côtés (`test/app.test.ts`, `lib/email.test.ts`) : la dérive serait silencieuse sinon. Le serveur reste l'autorité.
- **« Modifié » est un état du composant, pas une valeur du formulaire** : `{ ...valeurs }` part tel quel au serveur. Une fois modifiée, l'adresse n'est plus écrasée ; « Reproposer » (visible seulement si elle diffère de la proposition) revient à l'automatique.
- **Corrigé au passage (existait déjà) : l'erreur d'un champ non enregistré ne disparaissait pas.** `setValue(..., { shouldValidate })` ne valide que les champs enregistrés : après un envoi à vide, choisir le responsable laissait « Choisissez le responsable » affiché jusqu'au prochain envoi. Le responsable et le type passent maintenant par `trigger`.
- **Focus sur le premier champ en erreur**, dans l'ordre de la page, y compris le type et le responsable que la bibliothèque n'atteint pas (`shouldFocusError: false`, focus posé d'après les noms de champs, sans attendre l'affichage : une première version qui attendait `aria-invalid` ne fonctionnait pas dans Chrome). Aussi après une erreur du serveur (409 `email_pris`, 409 `licence_indisponible`, 400 par champ).
- **409 `licence_indisponible` : message sous le type de contrat** (il n'y a plus de champ licence), avec « libérez ou commandez une licence, puis renvoyez la demande ». Le formulaire ne montre pas le nombre d'unités libres : il faudrait une lecture de plus à l'ouverture, et le serveur reste l'autorité.
- **Fenêtre (shadcn `dialog`)** : 560 px, hauteur limitée à celle de l'écran avec défilement interne, pied fixe. Comme le panneau : un clic à côté ne ferme jamais, Échap ferme d'abord la liste des responsables, rien ne ferme pendant l'envoi. `radio-group` ajouté avec la procédure du dépôt (`radix-ui` déjà installé : aucune dépendance de plus, `npm audit` à 0). La modale ne produit aucun message en console ni violation de CSP (Chrome, bureau et mobile, derrière le vrai routeur).
- **Affichage** : pastille discrète à côté du nom (tableau, cartes, en-tête du détail) et ligne « Type de contrat » dans l'identité du détail. Rien dans la liste pour un compte d'avant le type (« Non renseigné » dans le détail), pour ne pas encombrer chaque ligne d'une absence. Le libellé de licence « réservée à la validation » devient « prévue, attribuée à la validation » (elle n'est plus choisie, elle est prévue).
- **Terraform** : `license_by_type` (objet `employe` / `contractor`), local `licenses_by_type_json`, réglage `LICENCES_PAR_TYPE`. `license_by_type` : chaque entrée est facultative (`optional(string)`, `null` = pas de licence prévue), validée contre les clés de `licenses` ; les entrées `null` n'apparaissent pas dans `LICENCES_PAR_TYPE` (`{}` si les deux le sont). **Sur `test` et `dev` : `employe = "business-premium"`, `contractor = null`**, faute de Business Basic dans le tenant (un SKU absent ferait échouer l'apply, `azuread_group_license`) : tant qu'il n'est pas acheté, créer un Contractor répond 409. Le message sous le type de contrat est celui de `licence_indisponible` (« Aucune licence disponible pour ce type de contrat : libérez ou commandez une licence… »), un peu large pour un type sans licence prévue, mais il évite un second code. Dès l'achat : ajouter `business-basic` à `licenses` et y pointer `contractor`. Aucune permission Graph ni rôle ne change : `User.ReadWrite.All` écrit déjà `employeeType` comme `jobTitle` et `department`.

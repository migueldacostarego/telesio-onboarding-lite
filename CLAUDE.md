# CLAUDE.md — Telesio Onboarding Lite

## Projet
MVP d'onboarding : RH saisit une demande → la direction valide → compte Entra (désactivé, attributs natifs) + dossier SharePoint → RH active le jour J (mot de passe temporaire remis en main propre ; changement imposé par Entra, Authenticator imposé par l'accès conditionnel). Pas de base de données : l'état vit dans l'extension Entra `statutOnboarding`. Détails : README.md.

## État
- Étapes 1 à 7 fusionnées sur main (licence par groupe : PR #3 ; activation par mot de passe temporaire et corrections du parcours : PR #5 ; droit Group.Read.All de l'identité d'apply : PR #4). Le TAP a été abandonné.
- Testé à la main sur test (2026-10-29) : à la 1re connexion, Authenticator puis changement du mot de passe imposés, passage à Terminé ; `User-PasswordProfile.ReadWrite.All` suffit. Réglages du tenant (à refaire à la main par tenant) : docs/reglages-tenant-onboarding.md.
- Envs test et dev déployés (tenant telesiosandbox, abonnement telesio-test). test s'applique à la main (`terraform apply` hors CI) ; dev par la CI à chaque fusion sur main. Dev n'a pas de site SharePoint dédié (validation en 503) : tester le parcours complet sur test. Prod inactive tant qu'il n'y a pas de vrai tenant.
- Stack : Node/TypeScript, App Service, Terraform (infra/), déploiement GitHub Actions en OIDC. Front : `web/` (Vite, React, TypeScript, Tailwind, shadcn/ui, React Router, TanStack Query), build dans `dist/web`, servi par Express sous `/app`.
- Front, étapes 2 à 4 faites sur la branche `feat/front-suivi` (PR #7) : l'écran « Demandes » (d'après `GET /api/suivi`) avec recherche, filtre, tri, actualisation 30 s, **actions** (Valider, Refuser, Activer, Régénérer, Réessayer le dossier ; le passage à Terminé est fait par une tâche du serveur toutes les 5 minutes, pas par l'écran), **Nouvelle demande** (panneau, react-hook-form, zod) et **panneau de détail** (quatre étapes, sous-états d'onboarding), avec en-tête, menu utilisateur (`GET /api/moi`) et gestion de session expirée / accès non autorisé. Tout est testé (Vitest) et contrôlé dans Chrome avec des données fictives, **jamais encore sur le tenant de test**. Choix, commandes et limites : README, section « Front React (/app) », et [DECISIONS-FRONT.md](DECISIONS-FRONT.md) (à relire : choix faits sans réponse pendant une session autonome).
- Avant la prod : le statut est une extension que tout administrateur d'utilisateurs peut écrire ; restreindre l'app (unité administrative à gestion restreinte) avant le vrai tenant.

## Prochaine étape : valider sur test, puis retirer les pages actuelles
- Parcours complet à faire à la main sur `test` avec l'écran `/app` (création, validation avec licence, activation, mot de passe, première connexion, Terminé), puis seulement retirer les pages-coquilles de `src/routes/pages.ts` (`/demande`, `/activation`, `/direction`, scripts inline de `src/views/layout.ts`) et rediriger vers `/app`. Elles restent en service jusque-là.
- Questions ouvertes (détail dans DECISIONS-FRONT.md) : recherche du responsable en `GET ?q=` (terme dans la requête de l'API) ; stepper horizontal dans la liste (la liste garde la barre « n sur 4 », le détail a la vue verticale) ; charte graphique toujours absente.
- Délais d'Entra, gérés côté écran (voir README) : 404 de `valider` sur un compte pas encore répliqué (« Compte en cours de création », nouvel essai automatique borné, car `GET /api/suivi` n'a pas de champ « prêt ») ; validation longue (spinner, ligne verrouillée) ; 202 `licence_en_cours` (revalidation à 60 s, bornée) ; passage à Terminé par la tâche du serveur (`src/terminaison.ts`, toutes les 5 minutes, une seule instance : pas de verrou partagé), qui s'ajoute aux événements `onboarding.termine_auto`.
- Ne jamais afficher ni stocker le mot de passe temporaire ailleurs que dans le DOM, une seule fois. Côté React : pas de `localStorage`, d'URL ni de cache de requête pour ce mot de passe. `activer` et `regenerer` passent par une mutation **sans observateur** (`executerSensible` dans `web/src/hooks/useActionsDemandes.ts`) : `gcTime: Infinity` pendant l'attente (avec 0, TanStack réarme un minuteur de 0 ms en boucle), `cache.remove` à la fin. Ne jamais les rejouer ; garder les tests qui vérifient cache, stockage, adresse, console et HTML.
- CSP de `/app` : `script-src 'self'`, `style-src 'self' 'nonce-…'`, aucun `unsafe-inline` ni `unsafe-eval` ni CDN, polices système, aucun message en console. Le nonce est aléatoire par requête, posé par Express sur `index.html` seulement (jamais en cache : `no-store`, pas d'ETag) et lu avant le rendu par `web/src/lib/nonce.ts` (`setNonce` de `get-nonce`) : c'est ce qui permet aux composants modaux de Radix (dialog, sheet, menu modal) de poser leur `<style>`. Pas de `<style>` ni de script écrits en HTML ni d'attribut `style` ; `style={{}}` de React est permis (CSSOM). Une bibliothèque qui crée un `<style>` sans `get-nonce` est bloquée (sonner, retiré) ; **zod doit rester en `jitless`** (`lib/demandeForm.ts`) sinon sa sonde `new Function` est une violation. Messages dans l'écran ou la ligne concernés, avec `alert` (`web/src/components/ApiErrorAlert.tsx`) ; pas de `next-themes`. Contrôler en Chrome (violations `securitypolicyviolation`, console) après tout ajout de composant ou bibliothèque d'interface, modaux ouverts compris, derrière le **vrai routeur** `src/routes/web.ts` (`dist/routes/web.js`) avec une fausse API seulement : un serveur statique ne prouve rien.
- Droits : l'interface décide d'après `droits` de `GET /api/moi` (`acces`, `creer`, `approuver`, `activer`, calculés côté serveur d'après `RH_ROLE` et `DIRECTION_ROLE`), jamais d'après le nom d'un rôle ; les noms ne sont écrits nulle part dans `web/`. Les routes de l'API décident d'après les mêmes droits (`droitsDe` : `creer` pour demandes, annuaire et licences ; `acces` pour le suivi ; `activer` pour activer, régénérer, terminer et la liste des activations); `approuver` pour `GET /api/demandes`, `valider` et `refuser`. Il n'y a plus de valideur désigné : tout porteur du rôle Direction peut valider ou refuser, sauf ses propres demandes (l'affectation du rôle, dans `direction_principal_object_ids`, désigne la direction). `GET /api/suivi` renvoie `actions` par demande pour la personne connectée (`approuver`, `refuser`, `activer`, `regenerer`) : l'interface ne propose que celles-là. Personne ne valide ni ne refuse sa propre demande (403 `auto_approbation`, créateur lu dans `createurOnboarding`).
- Charte Telesio : seul le logo est au dépôt (`web/src/assets/telesio.svg`, en-tête sur fond sombre car son texte est quasi blanc). Autres jetons : neutres de shadcn (`web/src/index.css`), à remplacer dès réception de la charte.

## Règles
- Zéro secret dans le code : identité managée partout (Graph, Key Vault).
- Permissions Graph minimales et justifiées (SharePoint en Sites.Selected).
- Dépendances publiées depuis plus de 7 jours, en version exacte (pas de `^`). Racine : `npm install --before=<date du jour - 7 j>`. `web/` : `web/.npmrc` impose `save-exact` ; ajouter avec `--before` aussi. Composants shadcn : `cd web && npm_config_before=<date> npm_config_save_exact=true npx shadcn@4.22.1 add <composant>` (le paquet `shadcn` n'est pas une dépendance : avis `npm audit`), puis vérifier `grep '[\^~]' package.json` et `npm audit --prefix web` (0 attendu). `react-hook-form` 7.90.0, zod 4.6.7 et `@hookform/resolvers` 5.9.2 sont installés (écran Nouvelle demande).
- Ne jamais commiter sans mon accord.
- PR avec CI verte avant toute fusion.
- Logs : jamais de nom, UPN ni mot de passe (seulement des objectId).
